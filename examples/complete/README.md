# Example: a Docker host on Proxmox

Everything needed to run `terraform-proxmox-docker-host` from scratch: a Route53 zone for the domain with the A
records, IAM Roles Anywhere for the DNS-01 challenge, and the module itself (VM, cloud-init, Traefik, runner, registry).
Fill in `variables.auto.tfvars` and apply.

```bash
cp variables.auto.tfvars.example variables.auto.tfvars   # edit: node, vm_id, ip, domain, acme_email, allowed_cidr, OIDC settings
export TF_VAR_proxmox_api_token='user@realm!tokenid=secret'
terraform init
terraform apply
```

Needs: an API token able to create VMs and download images on the node, SSH access to the node (the provider uploads
the cloud-init snippet over it), a free `vm_id` and a free static `ip` in the node's network, and AWS credentials for
Route53 and IAM (`aws_profile`).

The apply prints `ip` (the A records for the domain and its wildcard point to it) and `nameservers`: **delegate the
domain to them** (NS records in its parent zone). Until the delegation is in place Traefik cannot issue the wildcard
certificate (DNS-01) and the host is reachable only with a default certificate.

Credentials of the built-in registry (`enable_registry`, default `true`) are generated:

```bash
terraform output registry_url
terraform output registry_username
terraform output -raw registry_password
```

## Checking a fresh host

```bash
ssh ubuntu@<ip>                                    # needs ssh_public_keys; otherwise the console in Proxmox
cloud-init status --long                           # expect "status: done", no errors
docker ps                                          # traefik, runner, registry, ofelia
curl -s -o /dev/null -w '%{http_code}\n' https://registry.<domain>/v2/    # 401 without credentials
```

Deployments reach the host through `https://docker.<domain>/run-compose` with an OIDC token from the issuer
configured in `oidc_*`; the CI side is described in the `docker-host` core README. `allowed_cidr` must contain the
GitLab runners, the endpoint is not reachable from elsewhere.

## Notes

- cloud-init runs once: changing an input that ends up in it makes Terraform replace the VM. The registry hash is
  kept stable in `main.tf` for that reason.
- WAL-G has a bucket (`walg_backup_bucket`) and uses the same Roles Anywhere identity as DNS-01, no IAM user (`walg.tf`).
  The compose project must mount `/home/ubuntu/aws-roles-anywhere` at `/roles-anywhere` (read-only) into the containers
  that run wal-g; `walg_env_vars` of the module only point the AWS SDK at that profile. The private key is readable by
  gid 999 (`roles_anywhere_key_gid`): `archive_command` runs wal-g as the `postgres` user, which is not root. Empty the bucket before
  `terraform destroy`, it is not force-destroyed.
- No NAS mirror or Cloudflare tunnel here (`nas_host`, `cloudflare_tunnel_token` of the module): `/mnt/data` lives on
  the root disk, so `terraform destroy` removes the data with the VM, and so does every replacement of it.
- The DNS-01 challenge uses IAM Roles Anywhere (`roles_anywhere.tf`): the VM holds a client certificate and the
  role can change records only in this zone. The CA and client key are generated by the `tls` provider, so they are in
  the state and in the cloud-init snippet on the node; the client certificate lasts a year, after which Terraform
  issues a new one and replaces the VM. In real setups use your own CA or a shared identity.
- State is local. Configure a backend before keeping this environment.
